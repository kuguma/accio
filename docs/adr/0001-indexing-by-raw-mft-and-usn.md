# ADR 0001: 索引構築は $MFT の直接読み取り、差分追従は USN ジャーナル

- Status: Concept Only Approved (COA)
- 人間からの要求（原文）: 「インデキシング・検索それぞれについて、理論上それが最速であるように選択すること」「ジャンクションの無限参照、低速なFSやネットワークに律速されて固まる…落とし穴にハマらないように」「ユーザーにディレクトリを指定させたりしないこと」

## 演繹

NTFS 上の全ファイル名を得る方法は 3 つある。

| 方法 | コスト | 得られるもの |
|---|---|---|
| ディレクトリ走査 (FindFirstFileEx) | ディレクトリ数回のシステムコール、ランダム I/O | 名前・サイズ・日付。リンク循環・遅い FS・アクセス拒否の処理が必要 |
| `FSCTL_ENUM_USN_DATA` (Everything 1.4) | MFT を順読み、カーネルが整形 | 名前・親 FRN・属性のみ。サイズ・日付は別途ファイルごとに取得が必要（Everything の `index_size` が遅い理由） |
| `$MFT` を生で順読みしてレコードを自前解釈 (WizTree 等) | MFT のシーケンシャル読み 1 回 | 名前・親・属性・サイズ・作成/更新日時・ハードリンク全名、すべて 1 パス |

どの方法も MFT を 1 回読む I/O コストが下限であり、生読みはその下限に張り付きながら得られる情報が最大なので、これを採用する。
サイズと日付が初回スキャンで揃うことで「容量を占有しているディレクトリの一覧」もスキャン完了時点で提供できる。

差分追従は USN ジャーナル（`FSCTL_READ_USN_JOURNAL`）。変更ファイルのサイズ・日付は `FSCTL_GET_NTFS_FILE_RECORD` でその MFT レコードだけ読む。ファイルを開かないので、OneDrive 等のプレースホルダーをハイドレートさせない。

## 落とし穴への対応（調査結果 → 設計）

- ジャンクション/シンボリックリンクの循環: MFT 列挙はディレクトリを辿らないので構造的に発生しない。リパースポイントは属性つきの葉として索引する。
- 低速 FS / ネットワーク / 死にかけのデバイス: 対象は `DRIVE_FIXED` かつ NTFS のみ。ボリューム情報の問い合わせはボリュームごとに別スレッド＋期限付き（期限内に応答しないボリュームは今回は無視）。ネットワークドライブは索引しない。各ボリュームは専用スレッドで動き、互いにブロックしない。
- 同一ボリュームの多重登録（Everything.ini には同じボリュームが複数のドライブ文字で重複登録されていることがある（実例あり）されていた）: ボリューム GUID で一意化する。
- USN ジャーナルのラップ・ID 変更・未作成: 保存済み索引の `(journal_id, next_usn)` がジャーナルの有効範囲外なら、その索引は検索対象に残したままバックグラウンドで全再スキャンし、完了後に差し替える。ジャーナルが無ければ 128MB/8MB で作成する（voidtools 推奨値）。
- 8.3 短縮名: `$FILE_NAME` の名前空間が DOS(2) の名前は索引しない。
- ハードリンク: 1 ファイルの全長名を索引する（Everything 1.4 と同じ）。
- クラスタサイズ < レコードサイズのボリューム: MFT の論理オフセット空間でチャンクを切り、物理ランをまたいで読む。
- 権限: 生ボリューム読み取りと USN は管理者権限が必要。マニフェストで `requireAdministrator`。将来は Everything Service 相当の分離を検討（[[0004]] 予定）。

## 未決・再検討の余地

- ReFS（Dev Drive）には MFT が無い。`FSCTL_ENUM_USN_DATA` V3 経路が必要（未実装）。
- 削除されたハードリンクの別名は USN から特定できないことがある（Everything 1.5 も同様）。再スキャンで収束させる。
