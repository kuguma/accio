# ADR 0002: カラム指向索引・小文字化アリーナの SIMD 走査・zstd 並列永続化

- Status: Agent Working Decision (AWD)
- 関連: [[0001-indexing-by-raw-mft-and-usn]]

## 制約

- 1 文字入力ごとに 1 秒以内（計測機: 7950X 32 スレッド）。
- 起動から検索可能まで 2 秒以内。
- 索引のディスク/メモリ占有は Everything 1.4（この環境で DB 651MB・常駐 1.6GB）より小さく。

## 検索方式の選択

候補: (a) 全名前の連続バッファに対する線形部分文字列走査、(b) 接尾辞配列/FM-index、(c) n-gram 転置索引。

部分文字列検索の下限は「候補を 1 回ずつ見る」ことなので、ヒットが多いクエリ（1〜3 文字）では (b)(c) もヒット列挙が支配的になり線形走査と差がつかない。ヒットが少ないクエリでは (b)(c) が速いが、線形走査でも 15M 件・300MB を 32 スレッドの SIMD (memchr::memmem) で走査すると約 10〜40ms で、1 秒の予算に対して十分小さい。一方 (b) は索引を 4〜8 倍、(c) も 2 倍以上に膨らませ、更新コストも高い。したがって (a) を採用し、索引サイズを優先する。

計測（合成 15M 件、`cargo run --release -p accio-query --example bench -- 15000000`）:

| クエリ | ヒット | 時間 |
|---|---|---|
| `r` | 7.69M | 38ms（件数過多でソート省略） |
| `re` | 2.30M | 396ms（名前ソート込み） |
| `report photo` | 49K | 43ms |
| `ext:png` | 900K | 179ms |
| `path:backup` | 8.0M | 123ms |
| `regex:^rep.*\d{4}` | 542K | 149ms |
| `zzzz` | 0 | 11ms |

名前順は順列を事前計算し（11.4M 件で 0.9s、バックグラウンド）、ヒットが多いときは順列を歩いて O(N) で並べる（230 万ヒット: 396ms → 46ms）。

## 索引レイアウト

- エントリはカラム指向（parent/name_off/name_len/flags/attrs/size/mtime/ctime/frn）。検索ホット列は小文字化名の連続アリーナと parent。
- 原綴りは小文字化で変化した名前だけ別アリーナに持つ（ASCII 小文字名の二重化を避ける）。
- フルパスは保存せず、親チェーンから再構成する。表示行とパス一致検索のときだけ計算する。
- ディレクトリの `size` は配下合計（容量ビューの根拠）。USN 適用時は先祖チェーンに差分を加える。
- 主アリーナは追記専用で `name_off` 単調増加を保つ（走査ヒット位置→エントリは二分探索）。伸びるリネームは overflow へ退避し、保存時に詰め直す。
- 日時は 1970 起点の秒 (u32)、FRN は recno u32 + seq u16 に縮約した（索引形式 v2）。合成 15M 件でヒープ 1.16GB、ファイル 459MB。実機 C:（11.4M 件）の内訳は名前 312MB / 原綴り 73MB / ホット列 252MB / コールド列 約 250MB / by_recno 71MB。

## 永続化

カラムごとに zstd(level 1) 圧縮したセクションを並べ、読み込み時は全セクションを並列展開する。15M 件: 保存 1.5s / ファイル 492MB / 読み込み 0.81s。6 ボリューム並列でも I/O 帯域内に収まる見込み（NVMe）。
メモリマップではなく展開を選んだのは、ディスク上サイズを圧縮で半減させつつ、起動時間を予算内に収められると測定で確認できたため。

## 更新と並行性

- ボリュームごとに `RwLock<VolumeIndex>`。検索は読み取りロック、USN 適用と構築中の追記は短い書き込みロック。
- 構築中も追記済みエントリは検索できる（親未解決の間はパスを `…` 表示）。
- 再スキャンは別インスタンスを作って完了時に差し替える。旧索引は差し替えまで検索対象のまま。
